### N1 执行要点（0 成本，约十分钟）

**第 1 步：UptimeRobot 关键字监控（最该做的一项）**

- Monitor Type 必须选 **Keyword**（不是 HTTP(s)）：地址 `http://124.221.231.18`，关键字填「塔罗」。
- 原因：曾出现 80 端口被遗留 `sshd` 占用，访问返回 **HTTP 200** 但内容是 `SSH-2.0-OpenSSH_8.9p1`，纯状态码监控完全漏报（见归档 §10 第 4 项）。
- 间隔 5 分钟（免费版），通知=邮件；免费版不含短信/电话。
- 探测节点主要在海外，对国内 IP 偶有抖动，建议再补一条状态码监控交叉验证。

**第 2 步：腾讯云云监控告警策略**

- 资源阈值：CPU > 80%、内存 > 85%、磁盘 > 85%（持续 5 分钟）。
- 通知渠道绑微信公众号；短信每月 1000 条免费额度。

**第 3 步（可选，需改代码/脚本）**

- 配额告警：`quota:count:<当天>` 接近阈值（如 ≥ 40/50）时通知——成本熔断的最后一道闸。
- Redis 故障告警：当前 [upstash.ts](../lib/server/upstash.ts#L30) 用空函数吞掉所有 `error` 事件，Redis 挂掉会**静默降级**（配额/试用失效）且无人知晓。

**不建议**：自建 Uptime Kuma（监控与被监控同机，机器一挂两者同时失效）。

## 三、已知限制与风险（未解决）

- **无 HTTPS**（✅ 2026-09-16 已决策：接受现状）：公网 IP 直连只能用 HTTP，无法绑标准证书。除观感外有实质影响——用户自填的 DeepSeek Key、问题内容、`ADMIN_TOKEN` 均明文过网；如需 HTTPS，后续加域名 + ICP 备案 + SSL 证书（若届时采用 Q1 方案 A 的 Nginx，证书可直接在其中配置）。
- **HTTP 下 Web Crypto 受限**（✅ 2026-09-16 已决策：接受现状）：`crypto.subtle` 在非安全上下文不可用，API Key「记住」功能在 HTTP 下失效（刷新丢 Key），属固有限制，**上 HTTPS 才能恢复**（见归档 §6.2 连带说明）。
- **Redis / 服务器安全**：自建 Redis 虽只监听本机，仍需强密码；服务器只放行必要端口（22、80），建议 SSH 用密钥登录、`.env.local` 权限 600。
- **无调用日志**：出问题无法回溯「谁在什么时候用了什么」，只能看到计数（见归档 §14.1）。
- **公网 IP 持续被扫描**：`indigo-tarot-error.log` 中可见 `Failed to find Server Action "x"` 报错（2026-09-15 记录 4 条）——这是扫描器在探测 Next.js Server Action，本项目并未使用 Server Actions，Next 正确拒绝，**无实际影响**。属公网 IP 的正常背景噪音，但说明站点确实在被自动扫描（这也是及时升级依赖的理由之一）。
